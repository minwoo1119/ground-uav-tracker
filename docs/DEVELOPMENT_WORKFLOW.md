# GitHub 기반 개발 워크플로

이 문서는 프로젝트 소유자가 설계 의도, 코드 흐름, 기술 결정과 검증 결과를 이해한 뒤 변경을 병합할 수 있도록 Issue → 구현 계획 → 기능 브랜치 → Draft PR → 리뷰 → Merge 절차를 정의합니다. `AGENTS.md`가 최상위 규칙이며 이 문서와 충돌하면 `AGENTS.md`를 우선합니다. Agent가 실제 명령을 수행하는 순서는 `docs/AGENT_WORKFLOW.md`를 따릅니다.

## 1. 전체 흐름

```text
Issue 작성
  -> 문제·범위·완료 기준 합의
  -> Agent의 사전 구현 계획
  -> 필요한 사용자 승인
  -> 기능 브랜치에서 구현
  -> 로컬 검증
  -> Draft PR 작성
  -> 사용자 코드 리뷰와 이해 확인
  -> 필수 수정 및 재검증
  -> Ready for review
  -> 사용자 승인 후 Merge
```

Issue 승인 전에는 코드 구현을 시작하지 않습니다. 조사와 저장소 상태 확인 같은 읽기 전용 작업은 가능하지만, 설계 선택을 코드로 고정하지 않습니다.

## 2. Issue 기반 작업 관리

작업 성격에 맞는 Issue Form을 사용합니다.

- **Feature**: 사용자 동작, 인터페이스, 문서 또는 구조를 새로 추가하거나 개선할 때
- **Experiment**: 모델·알고리즘·설정 후보를 통제된 조건에서 비교할 때
- **Bug**: 기대 동작과 실제 동작이 다르고 재현 가능한 결함을 수정할 때

Issue는 최소한 문제, 범위, 완료 기준, 영향 모듈과 검증 방법을 포함해야 합니다. 하나의 Issue에는 독립적으로 리뷰하고 되돌릴 수 있는 작업 하나만 둡니다. 구현 중 범위가 커지면 원래 Issue를 조용히 확장하지 않고 후속 Issue로 분리합니다.

관련 Issue나 PR이 있는지 먼저 검색하며, 구현 PR은 본문에 `Closes #번호` 또는 적절한 연결 문구를 포함합니다.

## 3. Agent의 사전 구현 계획

Agent는 코드 작성 전에 Issue 댓글 또는 Issue 본문 갱신안으로 다음 계획을 제시합니다.

1. **현재 상태**: 관련 파일, 기존 호출 흐름, 테스트와 제약
2. **목표 동작**: 입력, 처리, 출력, 오류 동작
3. **변경 예정 파일**: 파일별 책임과 변경 이유
4. **호출 및 데이터 흐름**: 진입점부터 결과 소비자까지의 연결
5. **설계 결정과 대안**: 선택지, 트레이드오프, 추천안
6. **검증 계획**: 자동 테스트, 수동 명령, 실패 경로
7. **범위 밖 항목**: 이번 PR에서 다루지 않을 내용
8. **승인 필요 항목**: 사용자 결정을 기다리는 사항

계획은 함수 이름만 나열하지 않습니다. 데이터의 단위·소유권·유효 기간, timestamp/frame ID 유지, 오류가 어느 계층으로 전달되는지를 가능한 범위에서 설명합니다.

작은 문서 오탈자처럼 설계 판단이 없는 변경은 계획을 짧게 작성할 수 있지만, Issue 연결과 검증 결과는 생략하지 않습니다.

## 4. 사용자 승인이 필요한 변경

`AGENTS.md`에 따라 다음은 구현 전에 프로젝트 소유자의 명시적 승인이 필요합니다.

- 검출 모델 계열·크기·라이선스와 클래스 구성
- 카메라, 해상도, 화각, RTSP 등 입력 환경
- full-frame/ROI/tiling과 추론 주기
- 추적 알고리즘과 MOT 포함 여부
- JetPack/TensorRT/DeepStream 버전 및 배포 방식
- 성능 합격 기준과 로그 보존 정책
- 데이터 다운로드·학습·가중치 취득·외부 패키지 설치
- 카메라 이동, IR, 센서 융합, 외부 알림

다음 조건 중 하나라도 해당하면 Agent는 추천안과 대안을 제시한 뒤 승인을 기다립니다.

- 공개 인터페이스나 데이터 의미가 바뀐다.
- 새 외부 의존성, 네트워크 접근 또는 라이선스 의무가 생긴다.
- 성능·정확도·하드웨어 요구를 사실상 고정한다.
- 기존 데이터를 변환·삭제하거나 복구하기 어려운 Git 작업이 필요하다.
- Issue의 완료 기준이나 범위를 실질적으로 바꾼다.

일반적인 파일명, 내부 코드 스타일, 추가 다운로드가 없는 경량 테스트 구성 등 `AGENTS.md`에서 자율 결정 가능한 항목은 계획에 기록한 뒤 진행할 수 있습니다.

## 5. 기능별 Git 브랜치 관리

승인된 Issue마다 최신 기본 브랜치에서 별도 브랜치를 만듭니다.

| 작업 유형 | 브랜치 예시 |
|---|---|
| Feature | `issue/123-video-source-interface` |
| Experiment | `issue/124-input-size-comparison` |
| Bug | `issue/125-timestamp-order-error` |
| 문서 | `issue/126-workflow-guide` |

규칙:

- `issue/<번호>-<간단한-작업명>` 형식으로 Issue 번호와 짧은 kebab-case 설명을 사용합니다.
- 관련 없는 변경을 같은 브랜치에 섞지 않습니다.
- 생성 데이터, 모델, 엔진, 비밀 설정은 커밋하지 않습니다.
- 파괴적인 reset, force push, 기본 브랜치 직접 변경은 사용자 승인 없이 수행하지 않습니다.
- 커밋은 검토 가능한 논리 단위로 만들고 프로젝트에서 합의한 형식을 사용합니다.

Issue 기반 개발 요청에서는 `AGENTS.md`와 `docs/AGENT_WORKFLOW.md`에 따라 전용 브랜치 생성, 한글 커밋, 작업 브랜치 push와 Draft PR 생성을 수행합니다. 기본 브랜치 직접 push, Ready 전환, Merge와 원격 보호 설정 변경은 별도 승인이 필요합니다.

## 6. 구현과 로컬 검증

구현 중에는 Issue의 완료 기준을 테스트로 연결합니다. 정상 경로뿐 아니라 잘못된 옵션, 누락 파일, timestamp 역행처럼 사용자가 조치할 수 있는 오류 메시지를 검증합니다.

기본 C++ 검증 예시:

```sh
cmake -S . -B build -DUAV_ENABLE_TENSORRT=OFF -DUAV_BUILD_TESTS=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

실행하지 못한 플랫폼이나 테스트는 성공으로 표시하지 않습니다. 미실행 이유, 예상 위험과 사용자가 재현할 명령을 PR에 기록합니다.

## 7. Draft PR 작성

구현과 1차 로컬 검증 후 Draft PR을 만듭니다. PR 템플릿의 모든 항목을 실제 결과로 채웁니다.

특히 코드 흐름은 다음 질문에 답해야 합니다.

- 어떤 입력이 어디에서 들어오는가?
- 입력의 유효성을 어느 계층에서 어떻게 확인하는가?
- 내부 상태나 데이터 형식이 어떻게 변하는가?
- 정상 출력과 실패 출력은 무엇인가?
- 다음 모듈은 어떤 데이터와 식별자/timestamp를 받는가?

Draft PR에는 다음을 포함합니다.

- 관련 Issue와 승인된 구현 계획
- 변경 전후 동작과 파일별 역할
- 설계 선택 이유와 고려한 대안
- 실제 실행한 명령, 환경, 결과
- 미검증 플랫폼과 알려진 제약
- 사용자가 알아야 할 기술 개념
- 변경의 핵심을 확인하는 질문 2~3개와 해설

검증이 실패했거나 리뷰 준비가 끝나지 않은 동안에는 Draft를 해제하지 않습니다.

## 8. 사용자 코드 리뷰와 이해 확인

프로젝트 소유자는 다음 순서로 리뷰합니다.

1. Issue의 문제와 완료 기준이 여전히 유효한지 확인
2. PR의 입력 → 처리 → 출력 → 연결 흐름 확인
3. 공개 인터페이스, 오류 처리, timestamp 및 소유권 검토
4. 설계 대안과 트레이드오프 확인
5. 테스트 명령과 실제 결과 확인 또는 재실행
6. 이해 확인 질문에 답하고 해설과 비교

이해 확인 질문은 암기 시험이 아니라 설명의 빈틈을 찾기 위한 장치입니다. 사용자의 답과 해설이 다르면 Agent는 코드 변경을 강행하지 않고, 오해가 생긴 원인을 보완 설명하거나 문서·구조를 더 명확하게 수정합니다.

리뷰 의견은 가능하면 다음 중 하나로 구분합니다.

- **필수 수정**: 정확성, 안전, 범위, 테스트 또는 이해 가능성 문제
- **질문**: 코드 흐름이나 결정 이유 확인
- **제안**: 현재 Merge를 막지 않는 개선
- **후속 Issue**: 현재 범위 밖의 별도 작업

## 9. PR Merge 조건

다음 조건을 모두 만족해야 합니다.

- 연결된 Issue의 범위와 완료 기준을 충족한다.
- 사용자 승인이 필요한 결정을 승인 없이 고정하지 않았다.
- Draft 상태가 해제되었다.
- 필수 자동·수동 검증이 통과했고 실제 결과가 기록되었다.
- 미실행 검증과 알려진 제약이 명확하다.
- 코드 흐름, 설계 결정과 대안이 설명되어 있다.
- 관련 문서와 테스트가 갱신되었다.
- 비밀 정보, 외부 데이터, 모델, 엔진 및 생성 산출물이 없다.
- 필수 리뷰 의견이 해결되었다.
- 프로젝트 소유자가 코드 흐름과 핵심 기술 결정을 이해했음을 확인하고 승인했다.

Merge 방식과 브랜치 삭제 정책은 저장소 설정에서 소유자가 결정합니다. Agent는 별도 승인 없이 PR을 Merge하거나 기본 브랜치를 직접 변경하지 않습니다.

## 10. 작업 유형별 예시

### Feature 예시: 비디오 입력 인터페이스 확장

- Issue: 필요한 프레임 메타데이터와 오류 계약을 정의
- 계획: `IFrameSource` 입력/출력, 메모리 소유권 선택지와 테스트 범위 설명
- 승인 필요: 실제 카메라·RTSP·해상도를 고정한다면 사용자 승인
- PR 검증: 모델 없이 인터페이스 단위 테스트와 누락 입력 오류 확인

### Experiment 예시: 입력 크기 후보 비교

- Issue: 가설, baseline, 한 가지 변경 변수, 데이터 분할과 지표를 사전 등록
- 승인 필요: 모델·데이터 사용, 다운로드, 성능 기준
- PR/결과: 코드 리비전과 실행 환경, 원시 결과 위치, 측정값과 한계를 기록
- 주의: 데이터와 가중치, 엔진, 실험 출력은 Git에 커밋하지 않음

### Bug 예시: timestamp 역행 미검출

- Issue: 두 프레임의 timestamp와 실제/기대 오류를 최소 재현으로 기록
- 계획: 검증 책임 계층과 오류 전파, 회귀 테스트 설명
- PR 검증: 역행 입력은 구체적 오류를 반환하고 정상 순서는 기존대로 처리됨을 확인
- 후속 작업: 입력 장치 clock 정책 변경은 별도 Feature Issue로 분리

## 11. GitHub 저장소 설정 권장사항

프로젝트 소유자는 GitHub에서 다음을 설정합니다.

- 기본 브랜치 보호 또는 Ruleset
- PR 없이는 기본 브랜치에 병합할 수 없도록 제한
- 필수 승인 수와 stale approval 처리 방식
- CTest 기반 CI가 추가되면 해당 status check를 필수화
- force push와 브랜치 삭제 제한
- Merge 방식(squash, merge commit, rebase) 선택
- Issue/PR 라벨(`enhancement`, `experiment`, `bug`) 생성

외부 CI나 앱 연결은 별도 승인과 보안 검토 후 추가합니다.
